# OpenDoor — Project Brief

## One-line thesis

**OpenDoor determines whether a specific accessibility-sensitive outing is actually feasible by combining digital evidence with targeted, authorized CALL-E phone verification of critical physical-world constraints.**

## Product question

> **Can I actually go?**

## Why a phone call is indispensable

Some facts that matter to an outing are not stable, structured, or reliably published online. Examples include current elevator operation, temporary accessible-entry changes, current restroom availability, event-specific accessible seating procedures, and other operational details known by staff.

OpenDoor does not treat the phone as the product. The phone is a **targeted evidence-acquisition actuator**.

## What makes it different

The product is not:
- an accessibility directory;
- a venue accessibility score;
- a generic business verifier;
- an AI receptionist;
- a booking assistant.

It is a **constraint-aware outing feasibility engine** with CALL-E as the selective human verification mechanism.

## Locked MVP

One domain: accessible event outings.

One flow:

`request → constraints → digital evidence → critical gap → authorization → CALL-E → structured evidence → deterministic reconciliation → evidence brief`

## Trust model

- explicit provenance;
- timestamped evidence;
- categorical status;
- deterministic satisfaction policy;
- unknown is a real state;
- no global accessibility certification.

## Strongest product moment

The agent says:

> **“I could not verify this requirement, so I will not tell you that the outing is fully feasible.”**

## Strategic reason for lock

The project intentionally preserves the original ideation thesis while differentiating from existing CALL-E community patterns. The key differentiation is **whole-outing constraint composition and feasibility**, rather than generic phone verification.

## Fallback

If live CALL-E limitations block an individual feature, reduce scope or change implementation boundaries before changing the thesis. The first fallback is a more bounded event type, fewer constraints, or a controlled test venue—not a new product concept.
